```
## D-XXX: タイトル

- 日付: YYYY-MM-DD
- 状態: 採用 / 却下 / 廃止（廃止の場合は後継のDを記載）

### 背景
- なぜこの判断が必要になったか

### 決定
- 何を決定したか

### 理由
- なぜその選択をしたか（検討した代替案があれば併記）

### 影響
- この決定が及ぼす影響、制約
```

## D-002: 配信形式と構成

- 日付: 2026-10-15
- 状態: 採用

### 背景
- 指示書7.1は、PWA・ビルドなしの静的ファイル・GitHub Pages想定を第一候補とし、最終決定をPlannerに委ねている。PWAのインストールとService Workerにはhttpsが必要で、非公開リポジトリのGitHub PagesはGitHub Pro以上が必要になる。

### 決定
- PWA（ビルドなし・依存なしの静的ファイル、ES modules）を採用する。配信対象は `app/` 配下に置き、`docs/` や `.claude/` を公開しない。
- 配信先は、完成までGitHub Pages（リポジトリを公開）とする。その後、Cloudflare PagesまたはNetlify（非公開リポジトリのまま配信）へ移す可能性がある（ユーザー回答）。
- パスはすべて相対パスにし、配信先のサブパスに依存しない。localStorageのキーには `sf6memo.` の接頭辞を付ける（`*.github.io` はorigin共有のため）。
- 構成は `app/`（index.html、styles.css、app.js、core.js、sw.js、manifest、アイコン）、`tests/`（core.test.js、check.html）、package.json（依存なし、`node --test`）とする。`core.js` は純粋ロジック、`app.js` はDOMと入出力とし、それ以上は分割しない。
- ルーティングはhashで行う。

### 理由
- 利用端末がAndroidのみで、ビルド工程とストア手続きを避けられる。画面が5つ、状態が小さいため、フレームワークは不要と判断した（AGENTS.md判定ラダー）。

### 影響
- 7.3の基準5と7（オフライン起動・実機）の確認は、配信先が決まるT-013以降になる。
- 配信先の切替時は、パスが相対なので `app/` を配信ルートにするだけで済む。

## D-003: 保存先

- 日付: 2026-10-15
- 状態: 採用

### 背景
- 指示書4.3はlocalStorageを初期の保存先とし、データ消失への対策を求めている。

### 決定
- localStorageを使う。キーは `sf6memo.data`、`sf6memo.settings`、`sf6memo.drafts` の3つとし、文書全体をまとめて書き込む。
- `QuotaExceededError` では画面上で明示し、メモリ上の状態と下書きを保つ。
- 初回保存時に `navigator.storage.persist()` を呼ぶ。
- IndexedDBへの移行は、書き出しJSONが2MBを超えたときに行う。コードに `ponytail:` コメントで限界を明記する。

### 理由
- 同期的に読み書きでき、コードが最も短い。容量は個人利用に足りる（1件約1KBとして約5,000件）。

### 影響
- 保存形式を変えるときは `schemaVersion` を上げ、1回限りの移行処理を書く（AGENTS.md原則3の永続データの例外）。

## D-004: データモデル v1

- 日付: 2026-10-15
- 状態: 採用

### 背景
- 保存形式と表示形式を分ける設計原則（指示書第2節）に従い、トークン列の構造を確定する必要がある。

### 決定
- 文書は `app`、`schemaVersion`、`sections`、`combos` を持つ。コンボは `id`、`characterId`、`controlType`、`sectionId`、`title`、`position`（`any`／`corner`／`midscreen`）、`tokens`、`memo`、`tags`（文字列配列）、`favorite`、`createdAt`、`updatedAt` を持つ。
- トークンは `normal`（`stance`、`dir` 任意、`key`、`str`）、`special`（`motion`、`key`、`str`（ODを含む）、`stance` はjumpのみ）、`system`（`RAW_DR`、`CDR`、`DI`、`PARRY`、`REVERSAL`）、`sa`（`level`）、`note`（`CH`、`PC`）の5種とする。接続は保存しない。
- 投げ、待ち・移動、文字、ヒット数、技名ラベルはPhase 2で追加し、そのとき `schemaVersion` を上げる。
- 参照の整合（`characterId` はマスタに存在、`sectionId` は同じキャラのセクションを指す、idの重複なし）と文字列長の上限を、検証で強制する。
- 新しい版の `schemaVersion` を持つデータは拒否する。Phase 1では移行処理を書かない。
- セクションは `id`、`characterId`、`name`（1〜50文字）、`order`（0以上の整数）、`updatedAt` を持つ（取り込みで新しい方を残すために `updatedAt` が要る）。日時（`createdAt`、`updatedAt`）はエポックミリ秒の0以上の整数とする。
- `motion` の形式は `^(\[[1-9]\][1-9]+|[1-9]{2,})$` または `"360"`（`[4]6`、`[2]8`、`22` を含む）。プリセット外の方向列もこの形式を満たせば受け入れる。
- 取り込みのマージ後は参照整合を再検査しない。T-012では、マージ後の文書が `validateDoc` を通るときだけ反映する。

### 理由
- 意味を持つ最小単位で保存し、表記の好みは表示時に生成する。

### 影響
- 詳細なJSON例はPlannerの報告に基づき、`tests/core.test.js` の見本データで保持する。

## D-005: 表記と入力の規則

- 日付: 2026-10-15
- 状態: 採用

### 背景
- 指示書の3.2〜3.4に、実装を左右する未規定または曖昧な点があった（Plannerが洗い出し）。

### 決定
- OD: ボタン行はOD-PとOD-Kの2つにする（ボタン行は4×2）。OD-P／OD-Kの色はDesignerが決める。
- 方向入れの通常技: 方向パッドで1方向だけ押してからボタンを押すと、通常技の `dir` 修飾になる。2方向以上は必殺技のモーション、2のみは `stance: crouch` に正規化する。
- 姿勢・ペンディング中のモーション・方向は、ボタン1回で解除される1回限りの状態とし、画面に明示する。
- ▶は行動トークン同士の間にだけ入れる。注記（CH・PC）は直後の行動に付くタグとして表示する（列の先頭の注記は最初の技に付く。CHで始動、のように読む）。末尾に行動のない注記が残る間は、注記だけを仮表示する。注記と次の行動の間には▶を入れない。Phase 1のパッドで入力できる注記はCHとPCのみとする。
- id（セクション・コンボ）は `^[A-Za-z0-9_-]{1,64}$` に制限する。検証の理由メッセージには入力値を埋め込まない（画面表示時のXSSを避ける）。未知のキーを含む文書は拒否する。`motion` は20文字以内とする。
- 位置は `position` フィールドだけで持つ。注記トークンとタグの既定候補から「画面端」を外す（セクション候補の「画面端」は残す）。ユーザーが認めた。
- セクションの削除: 中身がある場合、他にセクションが無いうちは削除ボタンを無効にし、理由を表示する。
- ドライブパリィの略称は指示書どおりDPとする（ユーザー回答）。

### 理由
- 1技の入力タップ数の上限（3.4）を守り、同じ意味の情報の重複を避けるため。

### 影響
- 例外: プリセット外の方向列の技と、空中必殺技（J→プリセット→ボタンの3タップ）は、指示書の「3操作以上かかる」例に当たるが、3.4の表の上限内として許容する。

## D-006: 書き出しと取り込みの規則

- 日付: 2026-10-15
- 状態: 採用

### 背景
- 指示書4.4の取り込みの挙動は初期案であり、Plannerが確定する。

### 決定
- 検証は全件が通ったときだけ反映する。1件でも不正ならデータを変えず、理由を表示する。
- 対象は `sections` と `combos` のみとする。設定・下書き・最終書き出し日は端末ごとに持ち、取り込まない。
- idが一致する場合は `updatedAt` の新しい方を残す。同時刻なら端末側を残す。
- 削除は伝わらない。他の端末から取り込むと削除した記録が戻ることがある。個人利用のため許容する。
- 書き出しの案内は、最終書き出しから14日以上経ち、かつその後に変更がある場合のみ、キャラ選択画面の帯（［書き出す］［あとで］。［あとで］で7日間出さない）で控えめに出す（T-012で、toastから帯に変更）。
- 7.3の基準3の「全削除」は、アプリ内に機能がないため、ブラウザのサイトデータ削除で代替する。

### 理由
- データを失わせない（指示書第2節）。不正データによる部分的な破壊を防ぐ。

### 影響
- 取り込み前に「追加N件、更新M件」を表示して確認を取る。

## D-011: APK配布（Capacitorで包む）

- 日付: 2026-10-15
- 状態: 採用

### 背景
- ユーザーが、インストールアプリ（apk）としてダウンロードリンクを出せる準備を求めた。D-002は、apkが必要になったらPWAを後から包む形（TWAやCapacitor）で追加するとしている。

### 決定
- Capacitor（Android）で `app/` をそのまま同梱する。ビルド用の構成は `apk/`（package.json、capacitor.config.json、android/）と `.github/workflows/apk.yml` に置き、Webアプリ本体（`app/`）には依存を追加しない。
- appIdは `io.github.nagamaki0311.sf6memo`、アプリ名は「SF6戦略メモ」、縦固定、バー色は `#16140F`。Capacitor 8 の要件により、Android SDK 36、JDK 21 を使う。
- 署名は、環境変数（`KEYSTORE_FILE` ほか）があればリリース署名、なければデバッグ署名とする。配布前にユーザーがリリース鍵を作り、GitHubのSecrets（`ANDROID_KEYSTORE_BASE64`、`ANDROID_KEYSTORE_PASSWORD`、`ANDROID_KEY_ALIAS`、`ANDROID_KEY_PASSWORD`）に登録する。鍵はリポジトリ外にバックアップする。
- ワークフローは `workflow_dispatch` とタグ `v*` のpushで起動し、アーティファクトに加え、タグのときはGitHub Releaseに `sf6memo.apk` を添付する。ダウンロードリンクは `https://github.com/Nagamaki0311/strategy-memo/releases/latest/download/sf6memo.apk`（リポジトリが公開のとき有効）。
- JSONの書き出しはAndroid WebViewで `<a download>` と `navigator.share` が使えないため、`window.Capacitor?.isNativePlatform?.()` が真のときだけ `@capacitor/filesystem` と `@capacitor/share` 経由にする（T-012で実装。呼び出し例は apk/README.md）。

### 理由
- TWAは、GitHub Pagesのプロジェクトサイトではドメイン直下にassetlinks.jsonを置けず検証できない（URLバーが残る）うえ、ホスティングとPWAが先に要る。Capacitorはオフラインで動き、ホスティングに依存しない。

### 影響
- 署名鍵を登録しないと、Actionsの実行ごとに別のデバッグ鍵で署名される。署名が変わると上書き更新できず、アンインストールで端末内のlocalStorageのデータが消える。配布前に必ず鍵を登録する。
- ローカルでデバッグAPKとリリースAPKのビルドと中身の確認はできたが、実機での起動、Actionsの実行は未確認（T-016）。

## D-012: デザイン刷新v2（ネオン街）と合計ダメージ欄

- 日付: 2026-10-15
- 状態: 採用

### 背景
- ユーザーが、SF6公式のコマンドリストを参考にした全体のブラッシュアップ（ネオン管・ネオン街・暗い路地裏・電飾のモチーフ）、システム技の色分け（DI＝鈍い銀、DP＝紺、DR系＝蛍光グリーン、OD＝蛍光オレンジ）、キャラ選択画面の表記の作り変え、合計ダメージの入力と表示、入力完了の導線を求めた。メモ画面（編集画面）は現状のスタイルを維持する。

### 決定
- 仕様は docs/design-spec-v2.md とし、v1（docs/design-spec.md）の該当章を差し替える。要点: 地を `#0E0F11` に変更、発光はDR・OD（L寸法のみ）と記録があるキャラの名前に限定、システム技は種別ごとに色と形を変える、英字の看板書体はTilt Neon（SIL OFL 1.1）のサブセットをdata URIで埋め込む、キャラ選択は斜めのタイルの3列に英字とカナを併記、パッドのR1に［完了］キーを置き、閉じたパッドは格納バーまたはコマンド列のタップで開き直す。
- コンボに任意の `damage`（0〜99999の整数、未入力はキーなし）を追加する。D-004のコンボのフィールドに加える。`schemaVersion` は上げない（任意の追加で、既存の書き出しと取り込みはそのまま有効）。requirements 4.1のダメージ（Phase 2の付加情報）をPhase 1に前倒しする。
- requirements 3.3の「システム技・SA＝角丸の文字チップ」は、「システム技・SA＝文字チップ。種別ごとに枠の形を変える」に読み替える。ODの色は緑から橙に変わる（D-005のOD表示の色のみ）。Dリバの色はDPと同じ紺の二重枠、英字の表記はGOUKI・VEGA。
- ユーザー指示により、敵対的レビューは完成後に後追いで実行する。

### 理由
- ユーザー指示。発光を意味のある2種類に限り、requirements 5章の「理由なく既定にしない要素」との整合を保つ。

### 影響

## D-013: 使用感確認後の要望（デザインv2.1、前ステ・バクステ、強度指定なしのP・K）とデータ版2

- 日付: 2026-10-15
- 状態: 採用

### 背景
- 公開URLで使用感を確認したユーザーから、(1) キャラ名のフリガナを表示しない、(2) 記録が多いキャラほどネオンの発光と彩色を強める（段階を細分化）、(3) 前ステ・バクステの入力、(4) 強度の指定がないP・K（グレー）の入力、(5) 凡例を「〇に？」の控えめなヘルプマークに置き換える、(6) アプリアイコンを意図の分かる洗練されたブランドロゴにする、の要望があった。その後にT-015レビューを実施し、完成させてAPKを出す。ユーザーは約6時間不在で、判断を求められないため、未決事項は既定案で確定した。

### 決定
- 仕様は docs/design-spec-v2.1.md（v2.0に追加する章）とする。ネオンの段階は10段階（閾値 1/2/3/5/8/12/18/28/45/70、色は暖白→電球色→琥珀→赤橙の1本の軸）。静的な発光テキストの上限を35個に改める（ぼかし・不透明度・層数の上限は不変）。
- トークンの追加: `move`（`id` は `FWD_STEP`／`BACK_STEP`、表示は「前ステ」「バクステ」の破線枠の文字チップ）。`str` の値 `N`（強度の指定なし、無彩色の●）。D-004の「待ち・移動」のうち前ステ・バクステだけをPhase 1に前倒しする。
- パッドの高さを368pxから414pxに変更する（強度なしのキーの追加で5列になり、横8列×44px＝352pxが内幅348pxに入らないため。要件3.4の「画面の下半分」は、360×740で上端 y=326 とし、約56%に緩める）。
- 保存データの版を `schemaVersion` 2に上げる。版1のデータは変換なしでそのまま有効（読み込みと取り込みは版1と2を受け付け、書き出しは版2）。版3以上は拒否する。D-012の `damage` も版2に含める（版1のデータにdamageがあってもそのまま有効）。
- ブランドロゴは「看板と●」（傾けた1本のネオン管の枠＋●P）。アプリアイコン、PWA、APKに使う。

### 理由
- ユーザー要望。版を上げるのは、D-004の「トークンを増やすときに `schemaVersion` を上げる」方針に従い、古い版のアプリが新しいデータを黙って壊さず拒否できるようにするため。

### 影響
- 実機に入っている旧版のAPK（デバッグ署名）は、版2の書き出しファイルを取り込めない（「新しすぎる」で拒否）。新版を入れてから取り込む。
- e2eとcheck.htmlの寸法（パッド368→414、上端 y≥326）、`.cell` の選択方法（`aria-label`）を更新する。

## D-014: T-015レビューを受けた配信・保存・APKの方針

- 日付: 2026-10-15
- 状態: 採用

### 背景
- T-015の敵対的レビュー（観点A・B・C）で、Critical 0、High 1（署名鍵のコミットを誘う手順）、Medium 13が指摘された。

### 決定
- Service Workerの版数: `app/sw.js` の `CACHE` は、リポジトリ内では `sf6memo-dev`（ローカル開発用）とする。`.github/workflows/pages.yml` が、デプロイ時に `sw.js` 以外の `app/` の内容ハッシュで `sf6memo-<8桁>` に置き換える（コミットはしない）。手で版数を上げる運用は廃止する。デプロイの前に `npm test` を走らせ、失敗したら公開しない。置換の検査はe2e 19bに置く。
- 保存データ: 保存に失敗した操作は、画面・メモリとも巻き戻す（`commit` は書き込みの成功後に状態を更新する）。他タブで `sf6memo.data` が変わったら、取り消しトーストを閉じる。`sf6memo.settings` は、このタブで変えたキーだけを最新にマージして書き、他タブの変更でも読み直す。書き出しのJSONは整形なしにする（取り込み上限5MBとの食い違いを小さくするため）。
- 検証の追加: 空白のみのセクション名・タグ、`createdAt > updatedAt` を拒否する。下書きは、壊れた項目を新規の値で補い、tracksが不正なら捨てる。
- 署名鍵: ルートの `.gitignore` に `*.jks`、`*.keystore`、`*.p12`、`*.b64`、`keystore*`、`.claude/settings.local.json` を入れる。鍵はリポジトリ外（例: `~/keys/`）に作る。タグでpushしたときに署名鍵のSecretが空なら、`apk.yml` を失敗させる（手動実行は警告のみ）。Release作成は別ジョブにし、そのジョブだけ `contents: write`。
- APK: `android:allowBackup="false"`（「サーバーなし」の要件に合わせ、端末のバックアップにも出さない。機種変更・再インストールは書き出し・取り込みで移す）。`INTERNET` 権限は実機未確認のため残し、実機確認後に削除を検討する。FileProviderは cache のみにする。gradle wrapperの `distributionSha256Sum` を指定する。
- 見送り: CSP（CapacitorがWebViewの種類によってブリッジをインラインの `<script>` で注入するため、実機未確認で入れるとAPKの書き出しが壊れる恐れがある。実機確認後に再検討）、D-003の「2MB超でIndexedDB」の検知（`ponytail:` コメントのまま）。

### 理由
- レビューの指摘（再現手順つき）への対応。手動の版数管理は上げ忘れで全端末が古い版に固定されるため、デプロイ時の自動化に置き換えた。

### 影響
- ユーザーは、リリース署名鍵を作ってGitHubのSecretsに登録する（`apk/README.md`）。旧版（デバッグ署名）のAPKからは、書き出し→アンインストール→新APK→取り込みで移る。
- e2eの `EXPECT_CACHE` の固定値は廃止した。
