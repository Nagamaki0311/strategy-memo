```
## D-XXX: タイトル

- 日付: YYYY-MM-DD
- 状態: 採用 / 却下 / 廃止（廃止の場合は後継のDを記載）

### 背景
- なぜこの判断が必要になったか

### 決定
- 何を決定したか

### 理由
- なぜその選択をしたか（検討した代替案があれば併記）

### 影響
- この決定が及ぼす影響、制約
```

## D-002: 配信形式と構成

- 日付: 2026-10-15
- 状態: 採用

### 背景
- 指示書7.1は、PWA・ビルドなしの静的ファイル・GitHub Pages想定を第一候補とし、最終決定をPlannerに委ねている。PWAのインストールとService Workerにはhttpsが必要で、非公開リポジトリのGitHub PagesはGitHub Pro以上が必要になる。

### 決定
- PWA（ビルドなし・依存なしの静的ファイル、ES modules）を採用する。配信対象は `app/` 配下に置き、`docs/` や `.claude/` を公開しない。
- 配信先は、完成までGitHub Pages（リポジトリを公開）とする。その後、Cloudflare PagesまたはNetlify（非公開リポジトリのまま配信）へ移す可能性がある（ユーザー回答）。
- パスはすべて相対パスにし、配信先のサブパスに依存しない。localStorageのキーには `sf6memo.` の接頭辞を付ける（`*.github.io` はorigin共有のため）。
- 構成は `app/`（index.html、styles.css、app.js、core.js、sw.js、manifest、アイコン）、`tests/`（core.test.js、check.html）、package.json（依存なし、`node --test`）とする。`core.js` は純粋ロジック、`app.js` はDOMと入出力とし、それ以上は分割しない。
- ルーティングはhashで行う。

### 理由
- 利用端末がAndroidのみで、ビルド工程とストア手続きを避けられる。画面が5つ、状態が小さいため、フレームワークは不要と判断した（AGENTS.md判定ラダー）。

### 影響
- 7.3の基準5と7（オフライン起動・実機）の確認は、配信先が決まるT-013以降になる。
- 配信先の切替時は、パスが相対なので `app/` を配信ルートにするだけで済む。

## D-003: 保存先

- 日付: 2026-10-15
- 状態: 採用

### 背景
- 指示書4.3はlocalStorageを初期の保存先とし、データ消失への対策を求めている。

### 決定
- localStorageを使う。キーは `sf6memo.data`、`sf6memo.settings`、`sf6memo.drafts` の3つとし、文書全体をまとめて書き込む。
- `QuotaExceededError` では画面上で明示し、メモリ上の状態と下書きを保つ。
- 初回保存時に `navigator.storage.persist()` を呼ぶ。
- IndexedDBへの移行は、書き出しJSONが2MBを超えたときに行う。コードに `ponytail:` コメントで限界を明記する。

### 理由
- 同期的に読み書きでき、コードが最も短い。容量は個人利用に足りる（1件約1KBとして約5,000件）。

### 影響
- 保存形式を変えるときは `schemaVersion` を上げ、1回限りの移行処理を書く（AGENTS.md原則3の永続データの例外）。

## D-004: データモデル v1

- 日付: 2026-10-15
- 状態: 採用

### 背景
- 保存形式と表示形式を分ける設計原則（指示書第2節）に従い、トークン列の構造を確定する必要がある。

### 決定
- 文書は `app`、`schemaVersion`、`sections`、`combos` を持つ。コンボは `id`、`characterId`、`controlType`、`sectionId`、`title`、`position`（`any`／`corner`／`midscreen`）、`tokens`、`memo`、`tags`（文字列配列）、`favorite`、`createdAt`、`updatedAt` を持つ。
- トークンは `normal`（`stance`、`dir` 任意、`key`、`str`）、`special`（`motion`、`key`、`str`（ODを含む）、`stance` はjumpのみ）、`system`（`RAW_DR`、`CDR`、`DI`、`PARRY`、`REVERSAL`）、`sa`（`level`）、`note`（`CH`、`PC`）の5種とする。接続は保存しない。
- 投げ、待ち・移動、文字、ヒット数、技名ラベルはPhase 2で追加し、そのとき `schemaVersion` を上げる。
- 参照の整合（`characterId` はマスタに存在、`sectionId` は同じキャラのセクションを指す、idの重複なし）と文字列長の上限を、検証で強制する。
- 新しい版の `schemaVersion` を持つデータは拒否する。Phase 1では移行処理を書かない。
- セクションは `id`、`characterId`、`name`（1〜50文字）、`order`（0以上の整数）、`updatedAt` を持つ（取り込みで新しい方を残すために `updatedAt` が要る）。日時（`createdAt`、`updatedAt`）はエポックミリ秒の0以上の整数とする。
- `motion` の形式は `^(\[[1-9]\][1-9]+|[1-9]{2,})$` または `"360"`（`[4]6`、`[2]8`、`22` を含む）。プリセット外の方向列もこの形式を満たせば受け入れる。
- 取り込みのマージ後は参照整合を再検査しない。T-012では、マージ後の文書が `validateDoc` を通るときだけ反映する。

### 理由
- 意味を持つ最小単位で保存し、表記の好みは表示時に生成する。

### 影響
- 詳細なJSON例はPlannerの報告に基づき、`tests/core.test.js` の見本データで保持する。

## D-005: 表記と入力の規則

- 日付: 2026-10-15
- 状態: 採用

### 背景
- 指示書の3.2〜3.4に、実装を左右する未規定または曖昧な点があった（Plannerが洗い出し）。

### 決定
- OD: ボタン行はOD-PとOD-Kの2つにする（ボタン行は4×2）。OD-P／OD-Kの色はDesignerが決める。
- 方向入れの通常技: 方向パッドで1方向だけ押してからボタンを押すと、通常技の `dir` 修飾になる。2方向以上は必殺技のモーション、2のみは `stance: crouch` に正規化する。
- 姿勢・ペンディング中のモーション・方向は、ボタン1回で解除される1回限りの状態とし、画面に明示する。
- ▶は行動トークン同士の間にだけ入れる。注記（CH・PC）は直後の行動に付くタグとして表示する（列の先頭の注記は最初の技に付く。CHで始動、のように読む）。末尾に行動のない注記が残る間は、注記だけを仮表示する。注記と次の行動の間には▶を入れない。Phase 1のパッドで入力できる注記はCHとPCのみとする。
- id（セクション・コンボ）は `^[A-Za-z0-9_-]{1,64}$` に制限する。検証の理由メッセージには入力値を埋め込まない（画面表示時のXSSを避ける）。未知のキーを含む文書は拒否する。`motion` は20文字以内とする。
- 位置は `position` フィールドだけで持つ。注記トークンとタグの既定候補から「画面端」を外す（セクション候補の「画面端」は残す）。ユーザーが認めた。
- セクションの削除: 中身がある場合、他にセクションが無いうちは削除ボタンを無効にし、理由を表示する。
- ドライブパリィの略称は指示書どおりDPとする（ユーザー回答）。

### 理由
- 1技の入力タップ数の上限（3.4）を守り、同じ意味の情報の重複を避けるため。

### 影響
- 例外: プリセット外の方向列の技と、空中必殺技（J→プリセット→ボタンの3タップ）は、指示書の「3操作以上かかる」例に当たるが、3.4の表の上限内として許容する。

## D-006: 書き出しと取り込みの規則

- 日付: 2026-10-15
- 状態: 採用

### 背景
- 指示書4.4の取り込みの挙動は初期案であり、Plannerが確定する。

### 決定
- 検証は全件が通ったときだけ反映する。1件でも不正ならデータを変えず、理由を表示する。
- 対象は `sections` と `combos` のみとする。設定・下書き・最終書き出し日は端末ごとに持ち、取り込まない。
- idが一致する場合は `updatedAt` の新しい方を残す。同時刻なら端末側を残す。
- 削除は伝わらない。他の端末から取り込むと削除した記録が戻ることがある。個人利用のため許容する。
- 書き出しの案内は、最終書き出しから14日以上経ち、かつその後に変更がある場合のみ、キャラ選択画面の帯（［書き出す］［あとで］。［あとで］で7日間出さない）で控えめに出す（T-012で、toastから帯に変更）。
- 7.3の基準3の「全削除」は、アプリ内に機能がないため、ブラウザのサイトデータ削除で代替する。

### 理由
- データを失わせない（指示書第2節）。不正データによる部分的な破壊を防ぐ。

### 影響
- 取り込み前に「追加N件、更新M件」を表示して確認を取る。

## D-011: APK配布（Capacitorで包む）

- 日付: 2026-10-15
- 状態: 採用

### 背景
- ユーザーが、インストールアプリ（apk）としてダウンロードリンクを出せる準備を求めた。D-002は、apkが必要になったらPWAを後から包む形（TWAやCapacitor）で追加するとしている。

### 決定
- Capacitor（Android）で `app/` をそのまま同梱する。ビルド用の構成は `apk/`（package.json、capacitor.config.json、android/）と `.github/workflows/apk.yml` に置き、Webアプリ本体（`app/`）には依存を追加しない。
- appIdは `io.github.nagamaki0311.sf6memo`、アプリ名は「SF6戦略メモ」、縦固定、バー色は `#16140F`。Capacitor 8 の要件により、Android SDK 36、JDK 21 を使う。
- 署名は、環境変数（`KEYSTORE_FILE` ほか）があればリリース署名、なければデバッグ署名とする。配布前にユーザーがリリース鍵を作り、GitHubのSecrets（`ANDROID_KEYSTORE_BASE64`、`ANDROID_KEYSTORE_PASSWORD`、`ANDROID_KEY_ALIAS`、`ANDROID_KEY_PASSWORD`）に登録する。鍵はリポジトリ外にバックアップする。
- ワークフローは `workflow_dispatch` とタグ `v*` のpushで起動し、アーティファクトに加え、タグのときはGitHub Releaseに `sf6memo.apk` を添付する。ダウンロードリンクは `https://github.com/Nagamaki0311/strategy-memo/releases/latest/download/sf6memo.apk`（リポジトリが公開のとき有効）。
- JSONの書き出しはAndroid WebViewで `<a download>` と `navigator.share` が使えないため、`window.Capacitor?.isNativePlatform?.()` が真のときだけ `@capacitor/filesystem` と `@capacitor/share` 経由にする（T-012で実装。呼び出し例は apk/README.md）。

### 理由
- TWAは、GitHub Pagesのプロジェクトサイトではドメイン直下にassetlinks.jsonを置けず検証できない（URLバーが残る）うえ、ホスティングとPWAが先に要る。Capacitorはオフラインで動き、ホスティングに依存しない。

### 影響
- 署名鍵を登録しないと、Actionsの実行ごとに別のデバッグ鍵で署名される。署名が変わると上書き更新できず、アンインストールで端末内のlocalStorageのデータが消える。配布前に必ず鍵を登録する。
- ローカルでデバッグAPKとリリースAPKのビルドと中身の確認はできたが、実機での起動、Actionsの実行は未確認（T-016）。

## D-012: デザイン刷新v2（ネオン街）と合計ダメージ欄

- 日付: 2026-10-15
- 状態: 採用

### 背景
- ユーザーが、SF6公式のコマンドリストを参考にした全体のブラッシュアップ（ネオン管・ネオン街・暗い路地裏・電飾のモチーフ）、システム技の色分け（DI＝鈍い銀、DP＝紺、DR系＝蛍光グリーン、OD＝蛍光オレンジ）、キャラ選択画面の表記の作り変え、合計ダメージの入力と表示、入力完了の導線を求めた。メモ画面（編集画面）は現状のスタイルを維持する。

### 決定
- 仕様は docs/design-spec-v2.md とし、v1（docs/design-spec.md）の該当章を差し替える。要点: 地を `#0E0F11` に変更、発光はDR・OD（L寸法のみ）と記録があるキャラの名前に限定、システム技は種別ごとに色と形を変える、英字の看板書体はTilt Neon（SIL OFL 1.1）のサブセットをdata URIで埋め込む、キャラ選択は斜めのタイルの3列に英字とカナを併記、パッドのR1に［完了］キーを置き、閉じたパッドは格納バーまたはコマンド列のタップで開き直す。
- コンボに任意の `damage`（0〜99999の整数、未入力はキーなし）を追加する。D-004のコンボのフィールドに加える。`schemaVersion` は上げない（任意の追加で、既存の書き出しと取り込みはそのまま有効）。requirements 4.1のダメージ（Phase 2の付加情報）をPhase 1に前倒しする。
- requirements 3.3の「システム技・SA＝角丸の文字チップ」は、「システム技・SA＝文字チップ。種別ごとに枠の形を変える」に読み替える。ODの色は緑から橙に変わる（D-005のOD表示の色のみ）。Dリバの色はDPと同じ紺の二重枠、英字の表記はGOUKI・VEGA。
- ユーザー指示により、敵対的レビューは完成後に後追いで実行する。

### 理由
- ユーザー指示。発光を意味のある2種類に限り、requirements 5章の「理由なく既定にしない要素」との整合を保つ。

### 影響

## D-014: T-015レビューを受けた配信・保存・APKの方針

- 日付: 2026-10-15
- 状態: 採用

### 背景
- T-015の敵対的レビュー（観点A・B・C）で、Critical 0、High 1（署名鍵のコミットを誘う手順）、Medium 13が指摘された。

### 決定
- Service Workerの版数: `app/sw.js` の `CACHE` は、リポジトリ内では `sf6memo-dev`（ローカル開発用）とする。`.github/workflows/pages.yml` が、デプロイ時に `sw.js` 以外の `app/` の内容ハッシュで `sf6memo-<8桁>` に置き換える（コミットはしない）。手で版数を上げる運用は廃止する。デプロイの前に `npm test` を走らせ、失敗したら公開しない。置換の検査はe2e 19bに置く。

- 見送り: CSP（CapacitorがWebViewの種類によってブリッジをインラインの `<script>` で注入するため、実機未確認で入れるとAPKの書き出しが壊れる恐れがある。実機確認後に再検討）、D-003の「2MB超でIndexedDB」の検知（`ponytail:` コメントのまま）。

### 理由
- レビューの指摘（再現手順つき）への対応。手動の版数管理は上げ忘れで全端末が古い版に固定されるため、デプロイ時の自動化に置き換えた。

- e2eの `EXPECT_CACHE` の固定値は廃止した。

## D-016: キャラ選択の蓄積表現を「蛍光パネル」（蛍光グリーン）に置き換える。影のぼかしの例外

- 日付: 2026-10-15
- 状態: 採用（D-015のレベルメーター、D-013の琥珀の色の軸を置き換える）

### 背景
- ユーザーから、キャラ選択のタイルが件数の文字やメーターでメモの蓄積を表すのをやめ、マス目全体を発光・蛍光させる演出で表したい、メモが増えるほど徐々に（フェード気味に）強くしたい、色はドライブゲージを参考にした蛍光グリーンにしたい、との要望があった。3案（A 蛍光板、B ネオン管、C 蛍光パネル）の見本から、ユーザーが案Cを選んだ。ユーザー不在の間に、既定案で実装範囲を決めた。

### 決定
- 案C: 板（`.cell::before`）は暗い地のまま、縁から内側へ緑の光が滲む（`inset` の `box-shadow`）。段階が上がるほど滲みが板の中心へ届く。式と段階の色表は docs/design-spec-v2.1.md 1.2。段階0は現行の `--surface` で光なし。静的で、アニメーションなし。
- 英字は段階1以上で `--lit`（#EAFFF0、蛍光グリーンの白）、段階0は `--fg-muted`。弱いtext-shadow（1層、ぼかし l×0.6px・不透明度 l×0.05）を付ける。
- 件数の文字（`.cell-n`）とレベルメーター（`.cell-lv`）は削除する。件数は支援技術のために `aria-label`（「リュウ 3件」）に残す。段階の閾値と保存形式（schemaVersion 2）は変えない。
- 影の上限の緩和は1点だけ: キャラ選択タイルの板の内側への滲み（insetの1層）に限り、ぼかし12px・広がり6px・不透明度0.7以下まで認める。文字の影の上限（ぼかし8px以下ほか）、静的な発光テキスト35個、`filter`・グラデーション・アニメーション不使用は維持する。
- 実装範囲（既定案）: 段階の色表（`--nc`ほか）はワードマーク（`.wm`）と最近使ったキャラの英字（`.rc-en`）も使っていたので、同じ緑の軸に揃える（段階の `--tc` の色と弱い影）。ODの橙・DRの緑というコマンドのキー色の意味は変えない（DRの緑 #4DF27C との色の重なりは、ユーザーが見本を見たうえで承知して案Cを選んだので許容）。アプリのロゴ（枠の橙のネオン管と●P・●K）は変えない。
- 押下中の英字の点灯色（段階0〜2）は廃止し、板が `--line` に変わるだけにする。`--tx-lit` は廃止、`--lit` は #EAFFF0 にした（他に使う箇所がなかった）。

### 理由
- 件数とメーターを消す要望に対し、タイル全体の面で段階を読ませるのが案Cで、縁取りがなく「満ち具合」で読める。滲みを8px以下に抑えると、段階10でも光が板の中心まで届かず、段階の差が出ない（見本で確認）。内側への滲みは板の外へ出ない静的な塗りで、文字の発光（text-shadow）のコスト・可読性の問題とは別なので、この箇所だけ緩める。
- 実測（e2e 21b/21d、docs/progress.md）: 滲みを含む実画素の上でも文字との比は最小5.57（段階10）で4.5以上。32タイルすべて段階10でも、CPU 4倍・360×600のスクロールが60fps。

### 影響
- app.js の `charTile`（件数・メーターを外す）、styles.css の「ネオンの段階」節（全面更新）、tests/check.html と tests/e2e.mjs（メーター・件数の検査を、新仕様の検査に置き換え）。CLAUDE.md のデザイントークン節と docs/design-spec-v2.1.md 1章を更新した。
- 隣り合う段階の見分けは、レベルメーターという数の手がかりを失い、板の緑の濃さと滲みの幅だけになる（最小の差は0→1の板で、英字の色が変わるので一目で分かる。1→2の板は目立たないが、ユーザーが案Cの「フェード気味」を選んだ結果）。実機での見分けやすさはユーザーが確認する。

## D-017: 必殺技の技名（コマンドから技名を判定し、表示を切り替える）

- 日付: 2026-10-16
- 状態: 採用（第1段階の辞書とコア判定は実装済み。入力・表示のUIは第2段階 T-023）

### 背景
- ユーザーから、公式コマンドリストの「必殺技」の技名とコマンドを同梱し、コマンドとボタン強度から技名を判定したい、表示は「コマンド」と「技名」を切り替えたい、入力時もコマンドから候補を出して技名を選びたい、派生のある技（例: アルジュンの236Pのあとの6P）も扱いたい、との要望があった。仕様の正本は docs/design-spec-v2.2.md。

### 決定
- 表記は保存せず、表示のたびにそのキャラの辞書（app/specials.js）から引く。保存形式（schemaVersion 2）とトークンの形は変えない。技名も、派生かどうかも保存しない。
- 既定値（ユーザー不在の判断）: 設定「必殺技の表記」（`sf6memo.settings` の `specialNotation`、'cmd' か 'name'）の初期値は 'cmd'。入力パッドの［技名］キーの状態は保存しない。同じ入力に複数の技が当たるときはコマンド表示のままにする。連打・押しっぱなし・同時押し（ODを除く）・段入力（▶でつなぐ連続入力の2段目以降）は照合の対象外。
- 強度は、技名の先頭の接頭辞（弱・中・強・OD）で示す（当初は●との併記。●は D-019 で外した）。接頭辞は弱中強の区別がある技（辞書の `s` に弱中強のうち2つ以上）だけに付ける。強度が1つだけの技、強さの区別がない派生、強度ごとに技名が違う技（辞書の `v`）には付けない。強度なしは接頭辞なしで技名だけ。ODは辞書にOD版がある技だけ「OD」を付ける。ODのない技へのODと、強度別の技名の技へのODと強度なしは、技名なし（コマンド表示）。
- 派生の判定は design-spec-v2.2 5章のとおり。1件の記録のトークン列を先頭から引き、直前の行動（注記CH・PCを飛ばす。移動・システム技・SA・技名のない行動は「なし」）の判定結果が親で、親の強度条件・形（単一方向か方向なしの通常技、または同じモーション・ボタン・空中の必殺技）・派生自身の強度を満たすとき派生とする。連鎖（派生の派生）は深さの上限なし。同じ入力に派生が2つ以上当たれば技名なし。派生の条件を満たすトークンは、同じ形の単独の必殺技があっても派生を優先する。
- 辞書の形（app/specials.js、手で読めるESモジュール1ファイル、外部読み込みなし、約18KB）: キャラidごとの配列。項目は `{ name | v:{L,M,H}, motion, button:'P'|'K', s?, air?, follows? }`。設計書の `strengths` を `s`、`variants` を `v` と略した。`s` の省略は、必殺技なら弱中強OD、派生なら強さの区別なし。`follows` は `['親の技名', 親の強度条件?]`で、親は同じキャラの項目を技名（`v` の値のどれか）で引く。強度別の親（A.K.I.の紫煙砲）は条件で弱だけに絞る。
- 取り込みの規則: 次を除外する。複数ボタンの隣接（PP/KK/PPP/LP+LK 等）、段エントリ（技名なし）、入力表記なし、方向が文章のみ、ボタンなし、溜めのみ、複数の出し方が混在、親が必殺技欄にない・親が除外された派生、親がODで自身が通常技形の派生（通常技のトークンはODを表せず到達できない）。親が除外された派生は辞書に入れない（入れなければ当たらない。別の技へ親を付け替えて残さない）。件数は docs/progress.md。
- 強度ごとに技名が違う技（公式の強度明示行が2行以上、13組）は1項目にまとめ、`v` に強度→技名を持つ。公式はOD入力を画面に出さず、ドライブ消費アイコンからの推定なので、`v` の項目にはOD版の技名を持たせない（ODはコマンド表示）。
- 空中の技（`air`）の決め方: 公式データに空中の印がないため、技名に「空中」を含む、または注記に「ジャンプ中」を含むものを空中とする（18技）。名前に「エア」を含むが注記にジャンプがないエアスラッシャー（ディージェイ）とエアニースマッシュ（アレックス）は地上とする。空中の技はジャンプ姿勢のトークンにだけ当たり、地上の技はジャンプでは当たらない。
- 同じ入力が地上で複数の技に当たる組は、ジェイミーの流酔拳と流酔脚、酔疾歩と疾歩仙掌（段入力の最初の入力が同じ）、ザンギエフのロシアンスープレックスとシベリアンエクスプレス（近距離と遠距離）。いずれも技名なし（コマンド表示）になる。
- コアの関数（app/core.js）: `specialNames(tokens, characterId)`、`specialCandidates({ characterId, tokens, cursor, motion, jump })`、`specialLabel(token, info, mode, notation)`、`candidateLabel(candidate, notation)`、`hasSpecials(characterId)`、設定の `SPECIAL_NOTATIONS`・`DEFAULT_SPECIAL_NOTATION`・`sanitizeSpecialNotation`。

- 強度に応じて名前が変わる派生（`v`）が強度なしで決まらないときは、同じ形の単独の技へ落とさず「強さで変わる」にする（例: JPの214弱P ▶ 214P強度なしは、2つ目が技名なし）。単独の技の `v` が強度なしで決まらない場合の扱いは変えない。
- 方向なし（motion が null）の派生は、編集パッドで方向キー5を押したときの候補に出す（null は5）。

### 理由
- 保存しないので、辞書を直せば既存の記録の表示も直り、データ移行が要らない。トークンが同じなら複製・書き出し・取り込みでも表示が同じ。
- 強度の接頭辞に条件を付けたのは、辞書にない強度（強度が1つだけの技の「弱」など）を名前に出さないため。

### 既知の限界（ユーザーに伝える）
- 通常技の形の派生には、公式のドライブ消費アイコンが付くものが5件ある（ガイルのソニッククロス、ベガのヘッドプレス・デビルリバース、ヤスミンのウラン・クロッグ）。通常技のトークンはODを持てないので、OD版で出した入力はODなしの通常技として記録され、OD版だったことは記録に残らない。強度別の技名の技（`v`）のODは、公式にOD入力の記載がないので、常にコマンド表示になる。
- トークンには「派生かどうか」がなく、▶はキャンセルかつなぎかを区別しない。親の直後に同じ形の通常技を、受付が切れてから本当に通常技として出した場合も、派生として名前が付く。ポップオーバーに「〈親〉の派生」と出るので、判定の内容は確かめられる。直すには保存形式に印を足す必要があり、今回の前提（形式を変えない）の外。
- 辞書は公式ページの記載に基づく。公式にOD入力の記載がなく、ODの有無はドライブ消費アイコンからの推定。キンバリーの弧空（入力なしの自動派生）は除外したので、その先の武神イズナ落とし・武神鉾刃脚も辞書にない。
- クラシック操作の表記だけを取り込んだ（モダンは対象外）。ゲームの更新で技名・コマンドが変わると辞書は古くなる。

### 影響
- app/specials.js を追加し、app/sw.js のキャッシュ対象に足した（`CACHE` は配信時の置き換えなので触らない）。UI（app.js・styles.css）は第2段階。

## D-021: 連携・分岐のデータ方針（`parentId`、schemaVersion 3）

- 日付: 2026-10-16
- 状態: 採用（データ層はT-026で実装済み。UIはT-027）

### 背景
- ユーザー要望: コンボのあとの行動と分岐（例: コンボ → ガード時 → 投げ、ヒット時 → 追撃）を、木の形でメモしたい。連携・分岐も、コマンド列・タイトル・メモ・タグ・ダメージ・お気に入りを持つ既存の記録と同じ形にし、タイトルを見出し（「ガード時」など）に使う。

### 決定
- データ: 記録（`combos` の要素）に任意の項目 `parentId`（親の `id`。`ID_RE` に合う文字列）を足す。`parentId` のない記録が根（従来のコンボ）、あるものが連携・分岐。D-004のデータモデルに、この1項目を加える。
- 検証（`validateDoc`）: 親が文書内にある、親と同じ `sectionId`（セクションは1キャラのものなので、同じ `characterId` も保証される。`controlType` は `classic` だけ）、自分自身を親にしない、循環しない、深さは根を0として3以下（根 → 連携1 → 分岐2 → 分岐3）、1つの親の直下の子は8個まで。違反は `${i + 1}件目のcombosのparentIdが不正です(理由)` で拒否する。理由は固定文で、入力値を埋め込まない。上限は `LIMITS.depth`（3）と `LIMITS.children`（8）。親は配列の後ろにあってよい。
- schemaVersion: 3。書き出しは常に3。取り込みは1〜3を受け付け（版1・2は `parentId` を持たない文書として変換なしで有効。版1・2の文書に `parentId` があれば未対応の項目として拒否）、4以上は拒否する。マイグレーション関数はない。保存データ（`sf6memo.data`）の既存の版2は読み込み時にそのまま有効で、次の保存から版3になる。保存層（app.js の `loadData`・`commit`）は版の値を見ず、`parseDocText` と `exportDoc` を通すだけなので、app.js の変更は不要だった。
- 取り込み（`mergeImport`）: id一致は `updatedAt` の新しい方（D-006）。マージ後の文書を `validateDoc` に通し、親子の整合（親の存在・同セクション・深さ・個数）が崩れるときは取り込み全体を拒否する（データは変えない）。崩れるのは、片方の端末だけで根が別セクションへ移動された、片方だけが9個目の子を足した、親子が逆転して循環した、などの混在ケース。tests/core.test.js に固定した。
- 削除: 記録を消すと子孫も消える（`deleteCombo`）。取り消しは、呼び出し側が持つ削除前の state を書き戻す既存の仕組みのまま。確認文のために `countDescendants` で子孫の件数を返す。
- 複製: `duplicateTree` が子孫も新しい id で複製し、`parentId` を付け替える。連携・分岐の複製は同じ親の下の兄弟になるので、親の子がすでに8個なら例外（呼び出し側は `addChildBlock(combos, 子.parentId)` が null か事前に判定する）。子孫の `createdAt`・`position` は元のまま、`updatedAt` だけ now にする（兄弟の順序が保たれる）。複製した記録自身の `createdAt` は now。
- セクション移動: 根は `moveCombo` で子孫ごと移る。連携・分岐だけの移動は例外（根と別のセクションになり、検証にも通らない）。セクションの削除（`deleteSection`）は、根と子孫が同じ `sectionId` を持つので、そのまま一緒に移る。
- 兄弟の並び: 既存の `position` は画面位置（`any`／`corner`／`midscreen`）の列挙で、順序を持たないうえ、型を変えると保存形式の他の項目に触れる。兄弟は `createdAt` の昇順、同じなら `id` の順に並べる。新しい連携の `createdAt` は `nextChildCreatedAt`（now と兄弟の最大 `createdAt`+1 の大きい方）で決め、末尾に並ぶ。`newChildCombo` が `sectionId`・`characterId`・`controlType` を親から写し、`favorite` は false、`position` は 'any' にする。兄弟の並べ替えは行わない（将来作るときは、順序用の項目を足す決定が要る）。
- 件数: キャラ選択のタイルの件数・ネオン段階（`neonLevel` の入力）・読み上げ名の件数は、連携・分岐も数える（ユーザー決定。app.js は `combos` の全件を数えており、データ層に関数は足していない）。セクションの帯の「N件」と削除シートの件数は一覧に出す行の数で、`rootCount(combos, sectionId)`。セクションの全件は `comboCount`。一覧に出す記録は `rootsOf`（根と迷子）。
- 候補: `recentTokens`・`tagCandidates` は、そのキャラの全記録（連携・分岐を含む）から集計する。技名の判定（`specialNames`）は、記録ごとにコマンド列を単独で判定する（親のコマンド列を前置きしない）。変更は不要だった。

- 迷子: 親を最大3回たどって `parentId` のない記録に着けば木の中、着かなければ迷子（`isOrphan`）。`validateDoc` が拒否するので通常は起きない。UIの防御として、`rootsOf`・`rootCount` は迷子を根として含め、`addChildBlock` は迷子の下への追加を 'depth' にする。
- 追加できない理由: `addChildBlock(combos, id)` が null（追加できる）・'depth'・'siblings'・'missing' を返す。

### 却下した案
- 入れ子の配列（記録の中に `children` を持つ）: 記録のid一致によるマージ（D-006）が木の単位になり、片方の端末で子だけを編集した変更が、親ごとの置き換えで失われる。深さ・個数の検証も、各記録を平らに調べるより複雑になる。
- トークンの分岐（コマンド列の中に分岐を表す新しいトークンを置く）: 分岐ごとにタイトル・メモ・タグ・ダメージ・お気に入りを持たせる要望を満たせない。トークンの種類と、描画・技名判定・パッド入力のすべてに影響する。
- 参照による共有（連携を独立した記録にして、複数の根から参照する）: 同じ連携を再利用できる利点はあるが、削除・複製・セクション移動・取り込みのたびに参照元の追跡が要る。個人利用では、複製して使うほうが単純で足りる。

### 理由
- 1つの項目 `parentId` だけで木を表せ、各記録が既存と同じ形のままなので、描画・検索・マージ・書き出しの既存の仕組みをそのまま使える。深さ3・子8の上限で、画面に収まる木と、検証の計算量（線形）を保つ。

### 影響
- 実測（T-026、docs/progress.md）: 記録1万件・深さ3の木でも検証は約150ms、子孫の取得は1回約10ms。
- UIの作業（T-027）は、`deleteCombo`・`duplicateTree`・`moveCombo` を、app.js の削除・複製・編集の保存（セクション変更）に使う。現在の app.js は連携・分岐を持つ文書を扱わず、`removeCombo` が子孫を残して保存に失敗する、編集のセクション変更が検証に落ちる、などが起こるため、UIと同時に切り替える。
