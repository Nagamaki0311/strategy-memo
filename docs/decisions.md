# 設計判断記録 (ADR)

設計判断、採用理由、変更履歴を記録する。新しいエントリは末尾に追加する（古い順）。

## 記録フォーマット

```
## D-XXX: タイトル

- 日付: YYYY-MM-DD
- 状態: 採用 / 却下 / 廃止（廃止の場合は後継のDを記載）

### 背景
- なぜこの判断が必要になったか

### 決定
- 何を決定したか

### 理由
- なぜその選択をしたか（検討した代替案があれば併記）

### 影響
- この決定が及ぼす影響、制約
```

## D-002: 配信形式と構成

- 日付: 2026-10-15
- 状態: 採用

### 背景
- 指示書7.1は、PWA・ビルドなしの静的ファイル・GitHub Pages想定を第一候補とし、最終決定をPlannerに委ねている。PWAのインストールとService Workerにはhttpsが必要で、非公開リポジトリのGitHub PagesはGitHub Pro以上が必要になる。

### 決定
- PWA（ビルドなし・依存なしの静的ファイル、ES modules）を採用する。配信対象は `app/` 配下に置き、`docs/` や `.claude/` を公開しない。
- 配信先は、完成までGitHub Pages（リポジトリを公開）とする。その後、Cloudflare PagesまたはNetlify（非公開リポジトリのまま配信）へ移す可能性がある（ユーザー回答）。
- パスはすべて相対パスにし、配信先のサブパスに依存しない。localStorageのキーには `sf6memo.` の接頭辞を付ける（`*.github.io` はorigin共有のため）。
- 構成は `app/`（index.html、styles.css、app.js、core.js、sw.js、manifest、アイコン）、`tests/`（core.test.js、check.html）、package.json（依存なし、`node --test`）とする。`core.js` は純粋ロジック、`app.js` はDOMと入出力とし、それ以上は分割しない。
- ルーティングはhashで行う。

### 理由
- 利用端末がAndroidのみで、ビルド工程とストア手続きを避けられる。画面が5つ、状態が小さいため、フレームワークは不要と判断した（AGENTS.md判定ラダー）。

### 影響
- 7.3の基準5と7（オフライン起動・実機）の確認は、配信先が決まるT-013以降になる。
- 配信先の切替時は、パスが相対なので `app/` を配信ルートにするだけで済む。

## D-003: 保存先

- 日付: 2026-10-15
- 状態: 採用

### 背景
- 指示書4.3はlocalStorageを初期の保存先とし、データ消失への対策を求めている。

### 決定
- localStorageを使う。キーは `sf6memo.data`、`sf6memo.settings`、`sf6memo.drafts` の3つとし、文書全体をまとめて書き込む。
- `QuotaExceededError` では画面上で明示し、メモリ上の状態と下書きを保つ。
- 初回保存時に `navigator.storage.persist()` を呼ぶ。
- IndexedDBへの移行は、書き出しJSONが2MBを超えたときに行う。コードに `ponytail:` コメントで限界を明記する。

### 理由
- 同期的に読み書きでき、コードが最も短い。容量は個人利用に足りる（1件約1KBとして約5,000件）。

### 影響
- 保存形式を変えるときは `schemaVersion` を上げ、1回限りの移行処理を書く（AGENTS.md原則3の永続データの例外）。

## D-004: データモデル v1

- 日付: 2026-10-15
- 状態: 採用

### 背景
- 保存形式と表示形式を分ける設計原則（指示書第2節）に従い、トークン列の構造を確定する必要がある。

### 決定
- 文書は `app`、`schemaVersion`、`sections`、`combos` を持つ。コンボは `id`、`characterId`、`controlType`、`sectionId`、`title`、`position`（`any`／`corner`／`midscreen`）、`tokens`、`memo`、`tags`（文字列配列）、`favorite`、`createdAt`、`updatedAt` を持つ。
- トークンは `normal`（`stance`、`dir` 任意、`key`、`str`）、`special`（`motion`、`key`、`str`（ODを含む）、`stance` はjumpのみ）、`system`（`RAW_DR`、`CDR`、`DI`、`PARRY`、`REVERSAL`）、`sa`（`level`）、`note`（`CH`、`PC`）の5種とする。接続は保存しない。
- 投げ、待ち・移動、文字、ヒット数、技名ラベルはPhase 2で追加し、そのとき `schemaVersion` を上げる。
- 参照の整合（`characterId` はマスタに存在、`sectionId` は同じキャラのセクションを指す、idの重複なし）と文字列長の上限を、検証で強制する。
- 新しい版の `schemaVersion` を持つデータは拒否する。Phase 1では移行処理を書かない。

### 理由
- 意味を持つ最小単位で保存し、表記の好みは表示時に生成する。

### 影響
- 詳細なJSON例はPlannerの報告に基づき、`tests/core.test.js` の見本データで保持する。

## D-005: 表記と入力の規則

- 日付: 2026-10-15
- 状態: 採用

### 背景
- 指示書の3.2〜3.4に、実装を左右する未規定または曖昧な点があった（Plannerが洗い出し）。

### 決定
- OD: ボタン行はOD-PとOD-Kの2つにする（ボタン行は4×2）。OD-P／OD-Kの色はDesignerが決める。
- 方向入れの通常技: 方向パッドで1方向だけ押してからボタンを押すと、通常技の `dir` 修飾になる。2方向以上は必殺技のモーション、2のみは `stance: crouch` に正規化する。
- 姿勢・ペンディング中のモーション・方向は、ボタン1回で解除される1回限りの状態とし、画面に明示する。
- ▶は行動トークン同士の間にだけ入れる。注記（CH・PC）は直前の行動に付けるタグとして表示し、列の先頭にあるものは列全体の開始条件として表示する。Phase 1のパッドで入力できる注記はCHとPCのみとする。
- 位置は `position` フィールドだけで持つ。注記トークンとタグの既定候補から「画面端」を外す（セクション候補の「画面端」は残す）。ユーザーが認めた。
- セクションの削除: 中身がある場合、他にセクションが無いうちは削除ボタンを無効にし、理由を表示する。
- ドライブパリィの略称は指示書どおりDPとする（ユーザー回答）。

### 理由
- 1技の入力タップ数の上限（3.4）を守り、同じ意味の情報の重複を避けるため。

### 影響
- 例外: プリセット外の方向列の技と、空中必殺技（J→プリセット→ボタンの3タップ）は、指示書の「3操作以上かかる」例に当たるが、3.4の表の上限内として許容する。

## D-006: 書き出しと取り込みの規則

- 日付: 2026-10-15
- 状態: 採用

### 背景
- 指示書4.4の取り込みの挙動は初期案であり、Plannerが確定する。

### 決定
- 検証は全件が通ったときだけ反映する。1件でも不正ならデータを変えず、理由を表示する。
- 対象は `sections` と `combos` のみとする。設定・下書き・最終書き出し日は端末ごとに持ち、取り込まない。
- idが一致する場合は `updatedAt` の新しい方を残す。同時刻なら端末側を残す。
- 削除は伝わらない。他の端末から取り込むと削除した記録が戻ることがある。個人利用のため許容する。
- 書き出しの案内は、最終書き出しから14日以上経ち、かつその後に変更がある場合のみ、起動時にtoastで控えめに出す。
- 7.3の基準3の「全削除」は、アプリ内に機能がないため、ブラウザのサイトデータ削除で代替する。

### 理由
- データを失わせない（指示書第2節）。不正データによる部分的な破壊を防ぐ。

### 影響
- 取り込み前に「追加N件、更新M件」を表示して確認を取る。

## D-008: テストの方針

- 日付: 2026-10-15
- 状態: 採用

### 背景
- 非自明なロジックに最小限の自動確認を残す（AGENTS.md原則6）。依存は追加しない。

### 決定
- 純粋ロジック（`core.js`）は `node --test` と `node:assert` で検証する。依存は追加しない。

### 影響
- 実機での確認（7.3の基準5と7）はAgentには実行できないため、ユーザーによる確認のタスクとして置く。
