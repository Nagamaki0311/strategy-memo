# SF6戦略メモアプリ Claude Code向け実装指示

作成日: 2026年10月15日

この指示書は、Claude Codeが SF6戦略メモアプリを開発するための要件と手順をまとめたものである。project001から複製した新規リポジトリの `docs/requirements.md` として保存して使う。文体は、テンプレートの文体チェック（ja-style-check）に合わせて常体にしている。第8節の未回答5点には、回答がない場合の既定値を併記した。

## 1. 実行設定と開始手順

モデルはSonnet 5.5、effortはhighで起動し、project001を複製した新規リポジトリで `/init-project` から始める。

| 項目 | 設定値 | 指定方法 | 備考 |
| --- | --- | --- | --- |
| モデル | Sonnet 5.5 | `claude --model sonnet`、またはセッション中に `/model sonnet` | Anthropic APIでは `sonnet` がSonnet 5.5に解決される。Bedrock等のプロバイダーでは別バージョンになるため、固定する場合は `claude-sonnet-5-5` と書く |
| effort | high | `claude --effort high`、`/effort high`、環境変数 `CLAUDE_CODE_EFFORT_LEVEL=high`、設定キー `effortLevel` | Sonnet 5.5の既定は medium。明示しないと high にならない |
| 確認 | 起動直後 | `/model` と `/effort` | 表示がSonnet 5.5・highであることを確認してから作業を始める |

指定方法とエイリアスの解決先は、Claude Code公式ドキュメント（model-config）の2026年10月15日時点の記載による。

### ベースにするテンプレート

`Nagamaki0311/project001`（GitHub、非公開）は、Manager（ルートセッション）→ Planner → Developer → Reviewer の開発フローを持つClaude Code用テンプレートである。個別アプリの仕様と実装コードはproject001自体に入れず、複製した新規リポジトリで作る（README.md）。

テンプレートのAgentは役割ごとにモデルとeffortが固定されている。本プロジェクトでの扱いは次のとおり。

| Agent | テンプレートの設定 | 本プロジェクトでの扱い |
| --- | --- | --- |
| Manager | セッション設定に従う | 上表のとおり Sonnet 5.5 / high で起動する |
| Planner | opus / high | 既定を維持する。変更する場合は理由を `docs/decisions.md` にD-xxxとして記録する |
| Designer | opus / high | 既定を維持する。UI中心のアプリであり、デザイン判断の質が手戻り量に直結するため |
| Developer | sonnet / effort未指定 | `sonnet` はSonnet 5.5に解決される。effortはテンプレートの記述（docs/agents.md）に従いセッション設定を継承するため high になる。起動時に確認する |
| Reviewer | sonnet / high | 既定を維持する |
| Researcher | sonnet / medium | 既定を維持する |

環境変数 `CLAUDE_CODE_SUBAGENT_MODEL` が設定されていると全Agentが同一モデルで起動し、上表の固定が効かなくなる（docs/agents.md）。開始前に未設定であることを確認する。Planner・DesignerもSonnet 5.5 / highに揃えるかどうかはタスクの振り分け時にManagerが都度判断する（第8節で回答済み）。切り替えにはAgent呼び出し時の \`model\` パラメータを使う（docs/agents.md の「軽量レビューの扱い」と同じ方式）。恒久的に変更する場合は \`docs/decisions.md\` に、1回限りの切り替えは \`docs/progress.md\` に、判断と理由を記録する。

### 開始手順

1. ユーザーが `project001` から新規リポジトリを作成する。テンプレートリポジトリの設定が有効なら「Use this template」を使う。無効なら clone して `.git` を除いてコピーし、新規に `git init` する。リポジトリ名は第8節で確認する。
2. 新規リポジトリで `claude --model sonnet --effort high` を起動し、`/model` と `/effort` で設定を確認する。
3. `/init-project` を実行する。README.mdの「新規プロジェクトでの初期化」節に従い、docs/tasks.md・docs/progress.md・docs/decisions.md を初期化し、README.mdを書き換える。
4. 本書を `docs/requirements.md` として保存し、README.mdから1行で参照する。AGENTS.mdとCLAUDE.mdは毎セッション全文が読み込まれるため、アプリの仕様はそこへ書かず、必要な場面でだけ読まれるdocs配下に置く（CLAUDE.mdのトークン効率化ルール）。
5. 次の初回プロンプトを渡す。

```
docs/requirements.md を読み、AGENTS.md の開発フローに従って SF6戦略メモアプリの開発を始める。
最初のタスクは Planner による要件の矛盾・不足の洗い出しと、Phase 0〜1 の計画。
第8節の回答済み事項（Android、方向表記は矢印、接続記号は▶、モデルとeffortは都度判断）は変更しない。未回答の5点は推測で埋めず、既定値を採用する場合は docs/decisions.md に記録し、ユーザーの回答が必要なものは AskUserQuestion で確認する。3.6の投げ・投げ抜け・前ステ・バクステはコンボ表記の対象外で、確認は不要。
UI実装を伴うため、Planner は Designer の起動を提案する。
```

## 2. コンセプトと設計原則

コンセプトは「わかりやすく直感的なコンボルートとセットプレイを、簡単にメモして蓄積できるアプリ」である。仕様上の判断は、次の3つのこだわりに照らして行う。

| こだわり | 判断基準 | 基準を満たさない例 |
| --- | --- | --- |
| 1. コマンド表記のわかりやすさと入力の容易さ | 表記を読んだ人が、凡例を見ずに技の入力内容を言える。標準的なコンボ（5〜8トークン）を、第3節のタップ数で入力できる | 数字だけの表記を既定にして、数字の意味を覚えないと読めない。1技の入力に3操作以上かかる |
| 2. 直感的な操作性と迷わない閲覧 | 目的の記録まで「キャラ選択→一覧→詳細」の3画面以内で着く。各画面に主目的が1つだけある。主要操作が親指の届く画面下側にある | 記録を探すために検索語の入力が必須になる。閲覧画面と編集画面が同じで、誤って内容を変えてしまう |
| 3. 認知負荷の低いデザイン・UI・レイアウト | 同じ意味のものは常に同じ見た目にする。色だけに意味を持たせず、文字か形を併記する。画面内で最も重要な情報（コマンド列）を最も大きく見せる | すべてをカードに入れて階層が平らになる。装飾目的のアニメーションが入力の邪魔をする |

### 前提と範囲

- 利用者は現時点でユーザー本人のみとする。公開・配布・複数人での共有は前提にしない（第8節で確認する）。
- 対象ゲームはStreet Fighter 6のみとする。他タイトルへの対応は実装しない。dev.toの同種アプリの作者は、複数ゲーム対応でゲーム固有の入力をどう扱うかを課題に挙げている（Part 1時点）。SF6専用に絞れば、この課題を持ち込まずに済む。
- データは端末内に保存する。サーバーとアカウントは持たない。
- 初期版の範囲外は、アカウント、クラウド同期、他タイトル対応、動画の埋め込み再生、フレームデータの表示と計算、他ユーザーとの共有、Capcomの画像・ロゴ・アイコン素材の使用とする。

### 設計原則

保存形式と表示形式を分ける。表記の好み（矢印か数字か）や見た目は後から変わりうるが、蓄積したデータは変えたくないため、保存は意味を持つ構造化データとし、表示は保存データから毎回生成する。

最小の構成で始める。AGENTS.mdの判定ラダーに従い、依存ライブラリの追加とビルド工程は、必要性を示せるまで入れない。

データを失わせない。端末内の保存はブラウザ側のデータ消去で消えうるため、JSONの書き出しを初期版の必須機能にする。

デザインは題材から決める。テンプレートの `design-principles` に従い、「AIっぽい」既視感のある要素を理由なく既定にせず、使う場合は理由を仕様に残す（第5節）。

## 3. コマンド表記仕様

保存は構造化トークン列、表示はアイコンと日本語ラベル、入力はタップパッド、交換は数字（テンキー）表記テキストとする。この4層を分けることが、表記のわかりやすさと入力の容易さを両立させる前提になる。

### 3.1 先行事例から採る方針

| 先行事例 | 確認した内容 | 本アプリでの採用 |
| --- | --- | --- |
| 数字（テンキー）表記の解説 | 方向は1〜9の数字、5は入力なし、236や623でモーションを表す。「5」を技番号と混同しやすく、ゲームごとに対応が違う点が初心者のつまずきとして挙がる | 数字表記は交換形式に限り、既定の表示にはしない（既定の方向表記は矢印で確認済み） |
| dev.toのコンボメモ作者 | 既存サイトの `c.S > 2H > 236K` のような表記は直感的でないとし、ボタン表示と表記文字列の相互変換を目標にしている | 同じ方針とする。保存は構造化データ、表示と文字列は相互に変換する |
| Obsidian「FG Notation」 | 数字の連続を既知のモーションに最長一致で分解する。認識できない語は変換せずそのまま表示する。コピーボタンは生の表記を出力する | 取り込み時の分解は最長一致とする。未知の語は破棄せず文字トークンとして保持する |
| Reiketsu.net | 技名は「立弱P」「屈中K」のように日本語で書く。開始条件は括弧書き、状況は「画面端限定」等のタグで示す | 通常技のラベルと、開始条件・状況タグの分離を踏襲する |
| Capcom公式の技表・フレーム表 | 方向は矢印アイコン。ボタン強度は弱が水色、中が黄、強が赤で色分けされる。OD技は2ボタンのアイコン。連続入力する特殊技は「中K ▶ 強K」の形で書かれる | 矢印と色分けを踏襲し、技と技の接続は「▶」で表す。アイコンの絵は独自に描く |

### 3.2 保存形式（トークン）

コンボとセットプレイの手順は、意味を持つ最小単位（トークン）を並べた列として保存する。

| 種別 | 例 | 持つ情報 |
| --- | --- | --- |
| 通常技 | 屈中K、立ち強P、ジャンプ強K | 姿勢（立・屈・ジャンプ）、ボタン（弱・中・強 × P・K）。近・遠の距離違いと、方向入れ（引き強P、前中Kなど）は任意の修飾として扱う（近・遠は要確認） |
| 必殺技 | ↓↘→+強P | 方向列（モーション）、ボタン、ODの有無。任意の技名ラベルを付けられる |
| ターゲットコンボ | 強P▶強K、中P▶中P▶強P | 通常技を「▶」でつなぐだけで、専用のトークンは持たない。ターゲットコンボも通常技の並びとして保存する |
| システム技 | ドライブラッシュ、ドライブインパクト | 公式の名称に合わせ、略称は3.6の表に従う。種類は、パリィドライブラッシュ、キャンセルドライブラッシュ、ドライブインパクト、ドライブリバーサル、ドライブパリィ |
| スーパーアーツ | SA1、SA2、SA3 | 段階番号 |
| 投げ | 通常投げ、コマンド投げ | 種類 |
| 接続 | 「▶」の1種類のみ。技の間に自動で表示し、トークンとしては保存しない | 「次」の意味だけを持つ。キャンセル・目押し・そのあとは区別しない |
| 待ち・移動 | 歩き、ダッシュ、ディレイ nF | 種類とフレーム数（セットプレイ用） |
| 注記 | CH、PC、ヒット数、画面端 | 条件。カウンター（CH）とパニッシュカウンター（PC）を区別する |
| 文字 | 認識できない語 | 入力された文字列そのまま |

接続は「▶」の1種類とし、「次」の意味だけを持つ。種類の自動推定と手動切り替えは持たない。例: 屈中K▶236P、屈中K▶CDR▶立ち強P▶引き強P▶236強K▶SA3。種類の区別が必要になった場合は、接続に任意の注記を足す形で拡張する。

### 3.3 表示規則

| 要素 | 規則 | 理由 |
| --- | --- | --- |
| ボタン | ボタンは円（●）の中にP／Kの文字を入れて表し、円の色で強度を示す（弱＝水色、中＝薄い黄、強＝薄い赤）。例: 強P＝薄赤の●にP、屈弱K＝↓と水色の●にK。円の中の文字は円の色に対して4.5:1以上のコントラストを確保する。色だけに頼らない補助として、設定で円の隅に弱・中・強の小さな文字を出せる（既定はオフ） | 公式の色分けに合わせて読み取りを速くする。補助の文字を出せるため、色の見分けに差がある人にも読める |
| 方向 | 矢印アイコンを既定とする。矢印は軸のある太い線で描く。モーション（例 ↓↘→）と続く●は1つの技チップにまとめる。数字表記は設定で切り替える。モーションをタップすると「236 ＝ ↓↘→」の対応が出る | 公式の技表が矢印で表示しているため |
| 姿勢 | 立ちは何も付けず、しゃがみは↓、ジャンプは「J」の1文字ラベルを、●の前に付ける。書き出しテキストでは「立ち」「屈」「ジャンプ」と書く | 表示は、ユーザーが示した例（屈弱K＝↓と●K）に合わせる。テキストはReiketsu.netの「立弱P」「屈中K」に合わせる |
| OD | 技に「OD」の小ラベルを付け、ボタンを2つ表示する | 公式のOD技の表示に合わせる |
| 接続 | 接続は「▶」の1種類で表し、技チップの間に自動で挟む | コンボ表記として最も汎用的で、簡略化しても読み取れるため。方向の矢印は軸のある太い線、▶は軸のない小さな三角形とし、色も中間のグレーにして、形と濃さで区別する。▶の左右には、技チップの内側より広い余白を取る |
| 折り返し | 技チップ単位で折り返し、1つの技（モーションとボタン）の途中では折り返さない | 1つの技が途中で割れると別の技に見える |
| 大きさ | コマンド列を画面内で最も大きい要素にする。タップできるチップの最小サイズは44〜48px以上を目安とする | 認知負荷と誤タップの低減 |
| 凡例 | 全記号の意味を1画面にまとめ、詳細画面と編集画面から1タップで開ける | 初見の記号で止まらないようにする |

種類ごとの形を固定し、同じ形を別の意味に使わない。ボタン＝円（●）、方向＝太い矢印、システム技・SA＝角丸の文字チップ（DI、CDR、SA3）、接続＝軸のない小さな▶、注記（CH、PC）＝小さなタグ、待ち・移動＝点線の枠のチップ。表記の混同が起きないことは、7.3の基準で確認する。

### 3.4 入力方法（タップパッド）

入力には端末のソフトウェアキーボードを使わず、画面下部に固定した独自のパッドを使う。1技あたりのタップ数は次の表を上限とする。

| 入力する内容 | 上限タップ数 | 操作 |
| --- | --- | --- |
| 立ち通常技（例 立中K） | 1 | ボタンを押す（姿勢の既定は立ち） |
| しゃがみ・ジャンプ通常技 | 2 | 姿勢（↓・J）、ボタンの順に押す |
| 必殺技（例 ↓↘→+強P） | 2 | モーションのプリセット、ボタンの順に押す |
| OD必殺技 | 2 | モーションのプリセット、ODボタンの順に押す |
| プリセットにない方向列の技 | 方向の数＋1 | 3×3の方向パッドで方向を順に押し、最後にボタンを押す |
| 接続（▶） | 0 | 技の間に自動で入る。操作は不要 |
| 直前の入力の取り消し | 1 | 取り消しボタン（常に表示） |

検算用の例として、「屈中K▶236強P▶CDR▶屈中K▶236強P」の5技を9タップ以内で入力できることを受け入れ基準に含める（屈中K 2、必殺技 2、ドライブラッシュ 1、屈中K 2、必殺技 2）。この例は検算用であり、実在のコンボとは限らない。

パッドの構成は次のとおり。

- ボタン行は、弱P・中P・強P（上段）と弱K・中K・強K（下段）の6つにODを加える。各ボタンは3.3と同じ●の見た目（色と文字）にし、押したものがそのまま列に出るようにする。上段がP、下段がKという配置はSF6の標準的なボタン配置に合わせる。
- 姿勢の切り替えは、立ち（既定）・↓（しゃがみ）・Jの3択で、選択中の状態を明示する。
- モーションのプリセットのボタンは矢印（↓↘→など）で表示し、「波動」「昇龍」などの通称を小さく添える。数字は設定で切り替えたときだけ出す。プリセットの最初の候補は、236、214、623、41236、63214、360、↓↓、溜め入力（\[4\]6、\[2\]8）とする。公式技表で確認できた例は、→↘↓↙←（アルジュンの鬼気迫る尋問）、↓↓+強K（同、不撓の警衛）、↓↘→↓↘→（SA1）である。確定は、Researcherが全キャラの技表から必要な最小の集合を調べて行う。
- システム技（ドライブラッシュ、ドライブインパクト、パリィ、SA）は専用の行に置く。
- 入力した列のチップをタップすると、強度の変更、削除、その前への挿入ができる。入力中の列は、パッドの上に詳細画面と同じ見た目で表示する。パッドの上段には、このキャラクターで直近に入力した技を最大8件並べ、1タップで列に追加できる（保存済みの記録から作るため、新しいデータは持たない）。
- タップ直後に列の末尾へチップが現れること（体感で即時、目標は100ms以内）。
- 隣接するボタンの間隔を確保し、誤タップは取り消しですぐに戻せるようにする。
- パッドは画面の下半分に収め、片手の親指で届くようにする。

### 3.5 交換形式（数字表記テキスト）

書き出し・コピー・取り込みには数字表記のテキストを使う。

| 要素 | 表記 | 確認状況 |
| --- | --- | --- |
| 方向 | 1〜9（テンキーの配置）、5はニュートラル | 解説ページで確認 |
| ボタン | 弱P＝LP、中P＝MP、強P＝HP、弱K＝LK、中K＝MK、強K＝HK | 解説ページで確認 |
| 姿勢 | 立ちは5または接頭辞なし、しゃがみは2を前置（5LP、2LK）、ジャンプは `j.` を前置 | 立ち・しゃがみは解説ページ、`j.` はFG Notationの接頭辞で確認 |
| モーション | 236、623、41236、溜めは `[4]6` | 解説ページで確認。214は236の左右反転として同じ規則で扱う |
| 同時押し | `+` | 解説ページで確認 |
| OD | `OD236P` のように技の前に `OD` を置く | 本アプリ独自。SRK系wikiの凡例を開けなかったため、慣行との一致は未確認 |
| 接続 | 技の間は `▶`。取り込みでは `>` `,` `xx` なども `▶` として受け付ける | 本アプリの規則。書き出しは ▶ に統一する |
| 注記 | `CH`、`PC`、`(3)` ＝ ヒット数 | FG Notationの注釈で確認 |

接続の記号は参照元ごとに意味が異なる。解説ページでは `>` がキャンセルを表し、FG Notationは `>`、`,`、`xx`、`~`、`->`、`/` をすべて接続子として受け付ける。本アプリは接続の種類を区別しないため、取り込みではこれらと `▶` をすべて `▶` として扱う。

コピーと書き出しの既定は、ユーザーが示した日本語混在の形式とする。例: 屈中K▶CDR▶立ち強P▶引き強P▶236強K▶SA3。姿勢とボタンは日本語（立ち・屈・ジャンプ、弱・中・強 × P・K）、モーションは数字、システム技とSAは略称（3.6）で書く。ODは技の前に置く（OD236強P）。上表の英字略称（LP〜HK、5LP、j.）は、取り込みで受け付ける別名とする。

取り込みの規則は次のとおり。

1. 数字の連続は、既知のモーションに最長一致で分解する。
2. 認識できない語は破棄せず、文字トークンとして保持し、画面に「未認識」と表示する。
3. トークン列、テキスト、トークン列の往復で、元の列と一致することを自動テスト（アサーション）で確認する。

### 3.6 システム技の表記

共通のシステム技の名称・略称・入力を次に示す。略称は公式のものとは別で、ユーザーの調整を反映している。DRは単独だと意味が分かれるため、パリィ経由を生ラッシュ、キャンセル経由をCDRと分ける。CDRとSA3は、ユーザーが示した表記例で使われている。

| 名称 | 略称 | 入力 | 確認状況 |
| --- | --- | --- | --- |
| ドライブインパクト | DI | 強P+強K | 記事で確認 |
| ドライブパリィ | DP | 中P+中K | 記事で確認 |
| パリィドライブラッシュ | 生ラッシュ | ドライブパリィ中に→→ | 記事は「特定の動作中に→→」と記載。パリィ中という限定は補足 |
| キャンセルドライブラッシュ | CDR | →→。または(Nか→)+中P+中K（2023年7月24日追加） | 記事で確認。通常技・必殺技のキャンセルから出す |
| ドライブリバーサル | Dリバ | ガード硬直中に→+強P+強K | 2022年の記事による。その後の変更は未確認 |
| オーバードライブ | OD | 必殺技の入力時にボタンを2つ以上同時に押す | 記事で確認 |
| 投げ | 投げ | 弱P+弱K | コンボ表記の対象外。確認は不要 |
| 投げ抜け | 投げ抜け | 相手の投げに合わせて弱P+弱K | コンボ表記の対象外。確認は不要 |
| スーパーアーツ | SA1、SA2、SA3 | キャラクターごとに異なる | 共通の入力はない |
| 前ステップ・バックステップ | 前ステ・バクステ | →→、←← | コンボ表記の対象外。確認は不要 |

投げ、投げ抜け、前ステ・バクステはコンボルートに組み込まれない要素のため、コンボの表記では扱わず、入力の確認も不要とする。セットプレイでの投げと前ステ・バクステは、3.2の「投げ」と「待ち・移動」のトークンで扱う。3.4のシステム技の行は、この表の略称で表示する。

## 4. データモデルと保存

データは端末内のブラウザ保存領域に置き、JSONで書き出し・読み込みできるようにする。サーバーとアカウントは持たない。

### 4.1 エンティティ

| エンティティ | 主なフィールド | 導入時期 | 備考 |
| --- | --- | --- | --- |
| キャラクター（固定マスタ） | id、表示名 | Phase 1 | idは公式サイトのキャラクターURLのスラッグ（4.5）。キャラクターが追加されても、マスタのデータ1か所への追記で足りるようにする |
| コンボ | id、キャラクターid、操作タイプ（クラシック／モダン）、セクションid、タイトル、位置、トークン列、メモ、タグ、お気に入り、作成日時、更新日時 | Phase 1 | 操作タイプはReiketsu.netがクラシックとモダンで記事を分けているため踏襲する（第8節で確認） |
| セットプレイ | コンボと共通のフィールドに、分岐（相手の行動と、その結果の手順・メモ）を加える | Phase 2 | 連携（コンボ以外の攻めの連続した組み立て）は、同じ形で種別を分けて扱う |
| タグ | 名称 | Phase 1 | 状況タグ（画面端限定など）を既定の候補として持ち、自由入力もできる |
| 付加情報 | ダメージ、ゲージ（ドライブ・SA）、難易度、習得優先度、習熟度、動画URL | Phase 2以降 | Phase 1ではメモ欄で代替する。構造化する項目はPhase 2で絞る |

セクション（状況別項目）は、キャラクターごとにユーザーが作る1階層の入れ物で、フォルダに近い。フィールドはid、キャラクターid、名称、並び順で、コンボとセットプレイは必ず1つのセクションに属する。追加、名称変更、並べ替え、削除ができ、中身のあるセクションの削除では移動先を選ばせる。初期状態では空で、候補（通常、カウンター、パニッシュカウンター、インパクト壁やられ、スタン、画面端、起き攻め）から1タップで追加できる。候補はReiketsu.netの記事の分類を出発点にする。

### 4.2 コンボとセットプレイの違い

コンボは「セクション（状況）→ トークン列」の一直線の構造である。セットプレイは「開始状況 → 自分の手順（待ち・移動を含むトークン列）→ 相手の行動ごとの分岐」とする。開始状況は、どの技やコンボでダウンを取ったかで書く（Dustloopの起き攻め解説が、起点を「どのコンボや技でダウンを取ったか」で書いている）。

分岐は1段目までとし、深い木構造は持たない。dev.toの作者は、コンボ同士が要素を共有するため木に近いと述べているが、初期版で木構造を扱うと入力画面が複雑になる。必要になった時点で拡張する。コード上には `ponytail:` コメントで限界と拡張条件を残す。

相手の行動の例は、ガード、無敵技、投げ、バックステップ、ジャンプ、ドライブインパクトとする。固定の一覧にはせず、自由入力もできるようにする。

### 4.3 保存先と容量

初期版の保存先は `localStorage` とする。追加の依存がなく、同期的に読み書きできて単純である。容量はブラウザ既定で約5MBとされる。1件を約0.5KBと見積もると約1万件に相当し、個人の記録には十分である（見積もりは推定）。上限に近づいたら IndexedDB へ移行する。この制約は `ponytail:` コメントで明記する。

端末内のデータは、ブラウザのデータ消去やアプリの削除で消える。利用端末はAndroidと確認済みのため、iOS Safariの保存仕様は対象外とする。対策は次のとおり。

- JSONの書き出しをPhase 1の必須機能にする。
- 最終書き出し日を設定画面に表示する。
- 一定期間書き出していない場合に、起動時に控えめに案内する。期間はPlannerが決める。
- 永続ストレージの要求（`navigator.storage.persist()`）の利用を検討する。

保存データには `schemaVersion` を持たせる。保存形式の変更は、AGENTS.mdの原則3（後方互換性を維持しない）の例外である永続データに当たるため、互換レイヤーは作らず、1回限りの移行処理を書く。

### 4.4 書き出しと取り込み

- 書き出しは、全データをJSONファイルとして保存する。個別の記録は、数字表記テキストとしてコピーできる（3.5）。
- 取り込みでは、JSONを外部入力として検証する。形式が不正な場合は、データを変更せず理由を表示する。
- 取り込み前に「追加N件、更新M件」を表示して確認を取る。idが一致する記録は、更新日時の新しい方を残す。
- 端末間の移行は、JSONファイルの手動の受け渡しで行う。クラウド同期は範囲外とする。

上記の取り込みの挙動は初期案であり、Plannerが確定する。

## 5. 画面構成とUX

### 閲覧の設計

Reiketsu.netのコンボ記事は、番号と習得マーク、習得優先度、開始条件と状況タグ、入力リスト、解説、お気に入りと動画リンクの順に並ぶ。本アプリの詳細画面は、セクション名・位置・タグ、コマンド列、メモ、付加情報、操作の順にする。閲覧の目的はコマンド列を読むことであるため、コマンド列を画面内で最も大きく、最も目に入る位置に置く。

Reiketsu.netは状況による絞り込みとお気に入り登録を備えている。本アプリも同じ2つを一覧に置き、記録が増えても目的の1件へ着けるようにする。

### 操作の設計

- 主要な操作は、片手の親指が届く画面下側に置く（一般的なスマホUIの指針）。
- 画面遷移は、端末の戻る操作で直前の画面へ必ず戻れるようにする。
- 削除は実行後に数秒間「取り消し」を表示する。確認ダイアログは使わない。誤操作から戻る手順が短くなるため。
- 編集中の内容は下書きとして自動で保持し、「保存」で一覧に反映する。
- 保存の成功、保存領域の不足、取り込みJSONの不正は、画面上で明示する。

### レスポンシブとインストール

- 主な対象幅は縦持ちの360〜430pxとする。横持ちとタブレットは、崩れないことを条件にする。
- ノッチなどの安全領域に対応し、`viewport` を設定する。
- ホーム画面に追加でき、通信なしで起動できる（PWAの場合。形式は第7節）。

### デザイン方針（Designerが具体化する）

制作物の種類は「スマホアプリ」である。テンプレートの `design-principles` が示す優先要素は、タッチ操作、片手操作、操作速度、情報階層、画面遷移である。

次の要素は理由なく既定として使わない。使う場合は、理由を仕様に残す。

- 紫・青紫のグラデーション
- すべてをカードにする構成
- 過剰な角丸と過剰なドロップシャドウ
- グラスモーフィズムと意味のないグロー
- 巨大なCTAとSaaSテンプレート風のレイアウト
- 画一的なシステムフォントと意味のないアイコン
- 装飾だけが目的のアニメーション

Designerは、格闘ゲームの技術メモという題材から視覚方針を導く。SF6の公式UIや参考サイトの見た目は複製しない。Capcomの画像・ロゴ・アイコン・フォントは使わず、ボタンの記号は独自に描く。設定画面には、非公式のアプリでありCapcomとは無関係であることを1行で表記する（Reiketsu.netも自らを非公式ファンサイトとしている）。

- 配色・文字・余白のトークンはDesignerが仕様化し、Developerが対象アプリのCLAUDE.mdに記録する（docs/design-workflow.mdの手順）。`/design` が使える環境では、モックアップを生成してユーザーの確認を取る。
- 空の状態、読み込み中、エラー、保存済み、フォーカスの各状態を、通常状態と同じ水準で設計する。空の状態では、最初の1件を作る導線を置く。
- 文字と背景のコントラスト比は、WCAG 2.1 AAの基準である4.5:1以上を目安にする。
- アイコンには代替テキストを付ける。OSの「視差効果を減らす」設定に従い、動きを抑える。
- アニメーションは、入力の反応と画面遷移の方向を示す用途に限る。

## 7. 実装手順と受け入れ基準

Phase 1でコンボを入力・保存・閲覧できる最小版を作り、実機のスマホで操作を確認してから拡張する。

### 7.1 形式の方針

配信形式は、PWA（ホーム画面に追加できるWebアプリ）を第一候補とする。ユーザーは「ウェブでもapkでもよい」としている。PWAを第一候補にする理由は次の3点である。

1. コードベースが1つで済む。利用端末はAndroidと確認済みで、iPhone対応は初期版の対象外とする。
2. ビルド工程とアプリストアの手続きが要らない。
3. AGENTS.mdの判定ラダーに沿って、新規の依存を追加せずに済む。

apkが必要になった場合は、PWAを後から包む形（TWAやCapacitor等）で追加できる。ネイティブ開発（Kotlin等）、Flutter、React Nativeは、初期版の要件に対して構成が重く、第一候補にしない。最終決定はPlannerが行い、`docs/decisions.md` に記録する。

最初の構成は、ビルド工程と外部ライブラリを使わない静的ファイル（HTML、CSS、JavaScript）とする。フレームワークは、入力パッドの状態管理が静的ファイルでは保守できなくなった時点で、必要性を示して判断する。1ファイルが大きくなった場合は、AGENTS.mdの原則9に従い、検索用のアンカーコメントを置く。配信は静的ホスティング（例: GitHub Pages）を想定する。

### 7.2 フェーズ

| Phase | 内容 | 完了条件 |
| --- | --- | --- |
| 0 設計 | Planner: 要件の矛盾・不足の洗い出し、形式と保存先の決定。Designer: 画面とデザイントークンの仕様化。Researcher（必要時）: 第6節の調査依頼 | 決定が `docs/decisions.md` に、トークンがCLAUDE.mdに記録されている。第8節の未確定事項に回答があるか、既定値の採用が記録されている |
| 1 最小版 | キャラクター選択、セクションの作成、コンボの追加（タップパッド）、セクション別の一覧、詳細、編集、削除と取り消し、端末内保存、JSONの書き出し・取り込み、ホーム画面への追加とオフライン起動 | 7.3の基準1〜7を満たす |
| 2 拡張 | セットプレイ（分岐）、数字表記テキストの書き出し・取り込み、タグ・位置による絞り込み、お気に入り、構造化した付加情報（ダメージ・ゲージ） | 7.3の基準8を満たす |
| 3 候補 | 動画URL、習熟度、キャラクター別の技名プリセット（ユーザー提供のデータ）、練習中の画面常時点灯、apk化 | 必要性をユーザーに確認してから着手する |

### 7.3 受け入れ基準

1. 検算用の例（第3.4節）を9タップ以内で入力できる。
2. 入力、保存、再読み込みの後で、コマンド列が同じ表示になる。
3. 全データを書き出し、全削除し、取り込むと、元の内容に戻る。
4. 不正なJSONを取り込んでも、既存のデータは変わらず、理由が画面に表示される。
5. 機内モードで、起動、閲覧、編集、保存ができる。
6. 幅360px、390px、430pxの画面で、横スクロールが発生せず、コマンド列が折り返して読める。
7. 主要な操作（記録の追加、閲覧、編集、削除と取り消し）が、実機または実機に近いエミュレータで確認されている。技チップの種類（ボタンの円、方向の太い矢印、システム技の文字チップ、▶）が、色を見なくても形で区別できることを、スクリーンショットで確認する。
8. （Phase 2）数字表記テキストの往復変換が元の列と一致する自動テストが通る。

Reviewerは、REVIEW.mdの観点に加えて、`docs/design-workflow.md` の「Reviewerが確認するデザイン品質基準」を確認する。

### 7.4 作業の進め方

- Managerは、1タスクを確認できる1つの成果にする。状態は `docs/tasks.md`、作業履歴は `docs/progress.md`、設計判断は `docs/decisions.md` に記録する。
- 動作確認は、合否を返すチェック（テスト、画面幅別のスクリーンショット、ブラウザでの実操作）を実行し、実行内容と結果を証拠として残す（AGENTS.md）。
- 次の判断は `docs/decisions.md` に記録する。配信形式、保存先、トークンの構造、表記の規則、モデルとeffortの設定である。
- 表記の取り込み処理のように非自明な新規ロジックには、壊れたら失敗する最小限の確認（アサーション）を1つ残す（AGENTS.md の原則6）。
- 修正が2回失敗したら、コンテキストをリセットして状況を整理してから再着手する（CLAUDE.md）。
- 仕様を独断で変えず、不明点はユーザーに確認する（AGENTS.md のManager）。

### 回答済み（2026年10月15日）

- 端末OS: Android。iPhoneは初期版の対象外とする。

- モデルとeffort: 作業の振り分け時にManagerが都度判断して切り替える。テンプレートの固定設定は既定として残す。
- 接続記号: 「▶」の1種類（意味は「次」）。キャンセル・目押し・そのあとは区別せず、種類の自動推定も持たない。ターゲットコンボも同じ表記（強P▶強K）。
- 表記の見た目: ボタンは円の中にP／Kを入れ、色は弱＝水色、中＝薄い黄、強＝薄い赤。方向は太い矢印で、しゃがみは↓で表す（ユーザーの表示例による）。
